# 0023. Convenciones del esquema de base y del runner de migraciones

- Estado: Aceptado
- Fecha: 2026-11-01
- Issue: #32 (B-301)

## Contexto

El ADR 0004 fija PostgreSQL 16, Drizzle y migraciones SQL versionadas; el ADR 0006, `club_id` en todas las tablas y RLS; el ADR 0007, usuarios globales con membresías; el ADR 0010, Better Auth con tablas en nuestra base; el ADR 0015, `client_uuid` para que la sincronización sea idempotente, y el ADR 0017, `sport` y `sex` como enumeraciones cerradas. B-301 crea el primer esquema (`packages/db`) y deja sin definir varias cosas que afectan a todas las tablas que vengan: el tipo de los ids, cómo se garantiza que una fila no apunte a otro club, cómo se representan las enumeraciones sin duplicar el dominio, qué columnas de auditoría lleva cada tabla, cómo se nombran los rangos de fechas y cómo se corren las migraciones en el deploy.

## Decisión

- **Ids `uuid`** generados por la base (`gen_random_uuid()`), salvo las tablas de Better Auth (`user`, `session`, `account`, `verification`), que usan `text` como pide su esquema core, con el mismo default `gen_random_uuid()::text` y `generateId: 'uuid'` en Better Auth: todos los ids del sistema son UUID (los `UserId`, `ClubId`, `PlayerId` del dominio). Las tablas de Better Auth conservan sus nombres de modelo y de campo en TypeScript; las columnas SQL son `snake_case` como el resto. `is_superadmin` es una columna del usuario (atributo global, ADR 0007), expuesta a Better Auth con `input: false`.
- **Toda tabla con datos de un club** empieza con `id`, `club_id NOT NULL` y las columnas de auditoría, y tiene dos claves únicas: `(club_id, id)` y `(club_id, client_uuid)`. Las identidades globales (`user`, `session`, `account`, `verification`) y la raíz del tenant (`club`) son las únicas tablas sin `club_id`.
- **Integridad entre clubes en la base.** Las referencias entre tablas del club son claves foráneas compuestas `(club_id, x_id) → x (club_id, id)`: una fila del club A no puede apuntar a un jugador, una categoría o una sesión del club B, independientemente de la RLS (#33). Por defecto `ON DELETE RESTRICT` (los datos de menores se borran por flujos explícitos, B-329); `CASCADE` solo para hijas que no tienen sentido sin su padre (valores de un resultado, drills y participación de una sesión, ventanas de una temporada, asignaciones de una membresía). Cada clave compuesta tiene un índice que empieza por `(club_id, x_id)`.
- **Auditoría:** `created_at`, `updated_at` (`timestamptz`, mantenido por el trigger `set_updated_at` en cada `UPDATE`, también para SQL directo), `created_by` y `updated_by` (`user.id`, `NULL` para escrituras del sistema y `ON DELETE SET NULL`) y `client_uuid` (`NOT NULL`, default aleatorio para las escrituras del servidor). El historial de cambios con valor anterior y motivo es #36 (B-305).
- **Enumeraciones de Postgres derivadas del dominio.** Cada `pgEnum` se construye con la constante de `@sport-performance/domain` (`SPORTS`, `SEXES`, `STAGES`, `UNIT_CODES`, `MEASUREMENT_METHODS`, `ALERT_RULE_KINDS`…), así que agregar un valor en el dominio y correr `db:generate` produce el `ALTER TYPE … ADD VALUE`; un test de integración compara los enums de la base migrada con el dominio. Los vocabularios que la API también necesita y no existían (`MEMBERSHIP_ROLES`, `TEST_RESULT_STATUSES`, `TEST_NOT_DONE_REASONS`) se agregan al dominio. Los que hoy solo usa la base (tipos de consentimiento, estado de participación, nivel de contacto, tipos de dispositivo…) viven en `packages/db` con su constante exportada; si el dominio los necesita, la constante se mueve sin cambiar los valores ni las migraciones.
- **Fechas:** los instantes son `timestamptz`; los días del club son `date` leídos como `LocalDate` (`YYYY-MM-DD`) y nunca tienen default `current_date`, porque ese es el día del servidor y no el del club. Dos convenciones de rango con nombres distintos para no mezclarlas: tramos de calendario `starts_on` / `ends_on` (ambos inclusivos: temporadas y ventanas) y vigencias `valid_from` (inclusiva) / `valid_to` (exclusiva, `NULL` = abierta), como el `daterange '[)'` de las zonas de velocidad (B-209).
- **`CHECK` solo para invariantes duros** (bienestar 1–5, RPE 0–10, nota técnica 1–3, códigos `snake_case` sin "playerload", valores finitos, `not_done` con motivo, rangos con fin posterior al inicio). Los rangos plausibles son avisos del dominio, no restricciones: un valor raro confirmado por el staff es un resultado válido.
- **Valores derivados:** lo que es una expresión de una fila se guarda como columna generada (`srpe_au = rpe × minutes`); lo que necesita historia o fórmulas (maduración, EWMA, alertas) lo calcula el worker con el dominio y lo guarda con la ecuación o la regla que usó.
- **Migraciones:** `drizzle-kit generate` produce el SQL desde el esquema; lo que Drizzle no modela (triggers, y luego RLS, grants y el esquema `medical`) va en migraciones `--custom` dentro de la misma serie. Un test corre `drizzle-kit generate` sobre una copia de `drizzle/` y falla si el esquema y las migraciones no coinciden.
- **Runner:** `runMigrations()` (y el CLI `db:migrate`) aplica las migraciones pendientes con el migrador de Drizzle, cada una en su transacción, registradas en `drizzle.__drizzle_migrations`, bajo un advisory lock de sesión fijo: la API, el worker o dos réplicas pueden correrlo a la vez al arrancar o en el deploy y solo uno aplica. Se conecta con `MIGRATIONS_DATABASE_URL` (rol dueño de las tablas) o, si falta, `DATABASE_URL` (desarrollo y CI).
- **Tests de integración** contra Postgres 16 real: cada archivo crea su propia base temporal en el servidor de `DATABASE_URL` (Docker local, servicio de CI) y la borra al terminar. Sin `DATABASE_URL` se saltean localmente, pero con `CI` definido fallan.

## Alternativas descartadas

- **Texto con `CHECK` en lugar de enums de Postgres.** Es más fácil quitar un valor, pero ADR 0017 pide enumeraciones cerradas y extensibles por migración, y los enums dan el tipo en el esquema introspectado. Quitar un valor es raro y se puede hacer con una migración a mano.
- **Claves foráneas simples a `id`.** Más cortas, pero dejan que una fila de un club apunte a otro; la RLS lo ocultaría sin impedirlo.
- **Datos de referencia globales (`club_id NULL`).** Diccionarios, posiciones y reglas por defecto se siembran por club (B-306) desde el dominio: cada club los edita sin afectar a otros, y las políticas no necesitan un caso especial para filas compartidas.
- **`drizzle-kit migrate` en el deploy.** Es una herramienta de desarrollo (y `drizzle-kit` es una dependencia de desarrollo); el runner propio agrega el lock y se puede llamar desde el código de la API y el worker.

## Consecuencias

- Una tabla nueva sigue el patrón (`tenantColumns`, `tenantConstraints`, `tenantReference`) o el test de convenciones falla; además debe agregar el trigger `set_updated_at` en su migración, sus políticas RLS (#33) y sus tests.
- #33 agrega RLS, el rol de la aplicación sin privilegios y las funciones `app.*` sobre todas las tablas con `club_id`, en migraciones `--custom`. #35 agrega el esquema `medical`; #36, el historial de cambios; #37, los seeds; B-323, las columnas HLC y las marcas de borrado de las tablas sincronizables.
- Agregar un valor a un enum requiere que la migración que lo agrega no lo use en la misma transacción (limitación de `ALTER TYPE … ADD VALUE`): los seeds que lo usen van en una migración posterior.
