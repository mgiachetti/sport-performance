# 0033. Sesiones activas por dispositivo y aviso de ingreso nuevo

- Estado: Aceptado
- Fecha: 2026-11-02
- Issue: #142 (B-333)

## Contexto

La revisión OWASP de la API (`docs/security/api.md`, ASVS V3.3.3 y V3.3.4) dejó pendiente que una persona vea sus sesiones abiertas (web y mobile) y cierre las que no reconoce, que un admin pueda sacar a alguien al darlo de baja y que haya un aviso cuando se ingresa a la cuenta desde otro dispositivo. ADR 0028 fija Better Auth sobre su propia conexión (`sport_performance_auth`), sesiones de 30 días renovables sin cache en cookie y sin IP. Hacía falta decidir qué se guarda de cada sesión para que la persona la reconozca sin juntar datos de dispositivos de menores, cómo se reconoce un dispositivo "conocido" sin IP ni huella digital, qué alcance tiene el cierre por un admin cuando la persona es miembro de otros clubes y por qué conexión van esas consultas.

## Decisión

- **Qué guarda una sesión** (columnas nuevas de `session`, campos adicionales de Better Auth con `input: false`): `client_type` (`web` si la sesión viaja en la cookie, `mobile` si es bearer), `device_os` y `device_browser` (vocabularios cerrados de `packages/domain`, deducidos una sola vez del `User-Agent` al ingresar; `null` si no se puede) y `last_seen_at`. El `User-Agent` crudo y la IP no se guardan: dos `CHECK` de la base rechazan `ip_address` y `user_agent` con valor. Las sesiones solo se abren por `signInWithCode`, que le pasa el cliente al hook `session.create.before` de Better Auth; cualquier otro camino falla, así ninguna fila queda sin tipo de cliente. Las sesiones anteriores a la migración quedan como `web`.
- **Último uso con precisión de minutos:** `last_seen_at` se actualiza al autenticar solo si tiene más de 5 minutos, una escritura por sesión cada 5 minutos y no una por request. Si esa escritura falla, se loguea y el request sigue.
- **Endpoints propios** en `/v1/me/sessions` (nivel `session`): listar las sesiones vigentes propias, paginadas por cursor con `keysetPage` y `sort` por `createdAt` (las más nuevas primero por defecto; convenciones de listas del ADR 0032) y con la actual marcada; cerrar una (`DELETE /v1/me/sessions/{sessionId}`) y cerrar todas menos la actual (`POST /v1/me/sessions/revoke-others`). El id de sesión no es el token: conocerlo no abre nada. Una sesión ajena o vencida es `404`; la actual no se cierra ahí (`409`: para eso está `POST /v1/auth/sign-out`). Cerrar es borrar la fila, y como Better Auth lee la sesión de la base en cada request, el dispositivo queda afuera en el request siguiente. No se usan `listSessions` ni `revokeSession` de Better Auth: piden el token, que la API nunca expone.
- **Todo por la conexión de Better Auth.** El store de sesiones (`apps/api/src/auth/sessions.ts`) corre sobre `AUTH_DATABASE_URL` (`sport_performance_auth`); la conexión de la API sigue sin ver `session` ni `known_device`. Cada consulta se filtra por el usuario de la sesión autenticada, nunca por un id que mande el cliente.
- **Dispositivos conocidos** (`known_device`, global como las tablas de identidad, RLS forzada y solo para `sport_performance_auth`): por usuario, el SHA-256 de un id de dispositivo aleatorio, con su alta y su último uso. La web recibe ese id en una cookie propia `sp.device_id` (`__Secure-` con https, `HttpOnly`, `SameSite=Lax`, `Path=/v1/auth` para que solo viaje al ingresar, 400 días, el máximo que aceptan los navegadores). Mobile genera un UUID por instalación, lo guarda en el almacenamiento seguro y lo manda como `deviceId` al verificar el código. Un dispositivo sin uso por 400 días se olvida (y cuenta como nuevo aunque la poda todavía no haya corrido).
- **Aviso de ingreso nuevo:** si el dispositivo no es conocido para esa cuenta (o no trae id), la API manda un email por el `EmailTransport` (textos es-AR de `packages/i18n`) con el dispositivo ("Chrome en macOS", "la app en Android") y la fecha y hora en la zona del club de la persona (o la del país por defecto). El email no tiene links: dice que se abra la app o la web y se cierre la sesión desde "Sesiones activas", así no hay un link que se pueda imitar. La cuenta recién creada no recibe aviso: su primer dispositivo es el que la creó. El aviso es de mejor esfuerzo: la sesión ya está abierta, así que si el email falla se loguea (solo ids) y el ingreso responde igual. Cuando exista el worker (ADR 0011) el envío pasa a un job.
- **Baja de un miembro:** `revokeSessionsOfEndedMembership(auth, caller, membershipId, db)` es lo que llama el endpoint que da de baja una membresía (`POST /v1/club/members/{id}/end`, ADR 0034, por el hook `onMembershipEnded`). Exige la acción `revoke` de `membership` en la matriz de permisos (ADR 0025: el `admin` del club, o el superadmin en soporte) y una membresía de ese club (`404` si no). La membresía se lee en `db`, la transacción del request: mismo contexto de tenant y, para el superadmin, el acceso de soporte que esa transacción ya registró con su motivo (ADR 0029); no abre otra transacción con rol `superadmin`, que pediría el motivo de nuevo (issue #161). Si la persona no tiene otra membresía activa en ningún club y no es superadmin, se cierran todas sus sesiones. Si tiene otra, no se toca nada: la membresía dada de baja deja de valer en su request siguiente igual, porque cada request vuelve a leer las membresías activas, y un admin de un club no saca a nadie de otro. Funciona dentro o después de la transacción que da de baja, porque excluye la membresía dada de baja al buscar las otras.
- **Poda:** el mismo timer que limpia los límites de intentos borra las sesiones vencidas (Better Auth solo borra una vencida cuando alguien la usa) y los dispositivos sin uso por 400 días.

## Consecuencias

- La persona ve y cierra sus sesiones de web y mobile con datos que alcanzan para reconocerlas, sin IP ni `User-Agent` guardados; ASVS V3.3.3 y V3.3.4 quedan cubiertos.
- El reconocimiento del dispositivo depende de una cookie o de un id que guarda la app: si se borran las cookies, se usa una ventana privada o se reinstala la app, el siguiente ingreso se avisa como nuevo. Se prefiere un aviso de más a guardar huellas del dispositivo.
- Cada ingreso de mobile sin `deviceId` (versiones de la app anteriores a B-501) se avisa siempre.
- La app mobile tiene que mandar `deviceId` al verificar y conviene que mande `User-Agent: SportPerformance/<versión> (<ios|android>; …)` para que el sistema operativo salga bien (B-501).
- El endpoint de baja de membresía, cuando se haga, llama a `revokeSessionsOfEndedMembership`; la decisión de no cerrar sesiones de quien sigue en otro club queda acá.
- `known_device` es una tabla global más: entra en las listas de tablas globales y de Better Auth de los tests de catálogo.
