# 0031. Endurecimiento de la API: límites generales, headers, validación estricta, secretos y timeouts

- Estado: Aceptado
- Fecha: 2026-11-01
- Issue: #63 (B-332)

## Contexto

ADR 0028 (#40) dejó cubierto el ingreso: límites de intentos propios en Postgres con claves HMAC, CORS con credenciales solo para `WEB_ORIGINS`, guard de origen contra CSRF, cuerpos solo JSON y `TRUST_PROXY_HOPS` para ver la IP real. El resto de la API no tenía límite de requests, no mandaba headers de seguridad, aceptaba (y descartaba en silencio) claves desconocidas en los cuerpos, no limitaba el tamaño por tipo de endpoint, aceptaba en producción secretos débiles o de ejemplo y dejaba los timeouts del servidor HTTP en los valores de Node. Antes de producción hace falta cerrar eso y dejar una revisión OWASP (ASVS y API Security Top 10) que apunte a código y tests.

## Decisión

- **Límites generales en todos los requests**, por IP siempre y por usuario cuando hay sesión, con ventana fija de un minuto y **clases de ruta**: `public` (300 por IP), `auth` (endpoints públicos que cambian estado: 60 por IP), `read` (GET con sesión: 600 por usuario, 1200 por IP), `write` (600 por IP, 120 por usuario), `upload` (reservada para las URLs firmadas de B-325: 120 por IP, 30 por usuario) y `exempt` (solo `/health/live`, `/health/ready` y los preflights `OPTIONS`). Cada clase tiene sus contadores. La clase sale del nivel de auth y del método del endpoint (`registerEndpoint`) y se puede fijar por ruta; una ruta que no es del contrato o un 404 cuentan como `public` o, con sesión, `read`/`write`. Los límites del ingreso de ADR 0028 no cambian y se suman.
- **Mismo store que ADR 0028**, detrás de la interfaz `RateLimiter` (ahora `hit(checks)`): la tabla `auth_rate_limit` con el login de `sport_performance_auth`, claves HMAC con `AUTH_SECRET` y prefijo `api_`, todos los contadores de un request en **un solo `insert … select from unnest … on conflict`**, una transacción por request. Sin migración nueva. Hay un store en memoria con la misma semántica solo para tests.
- **El límite general falla abierto**: si el store falla o tarda más de `RATE_LIMIT_TIMEOUT_MS` (500 ms), el request pasa y se loguea un warning. Protege capacidad; no puede convertir una base lenta en una caída total. Los del ingreso siguen fallando cerrado (un error ahí es un `500`), porque protegen cuentas.
- El límite corre en el hook `onRequest` **después de autenticar**, para contar por usuario sin un segundo viaje a la base. Un flood con tokens inventados cuesta una búsqueda de sesión por request, del mismo orden que contar antes.
- **`429 rate_limited` con `Retry-After`** en el sobre del contrato. `rate_limited` pasa a ser un error implícito de todos los endpoints en el contrato; el OpenAPI documenta el header en los `429` y el cliente tipado lo expone como `ApiError.retryAfterS`.
- **Headers de seguridad propios** (el conjunto de helmet acotado a una API JSON), en el primer hook `onRequest` para que también los lleven errores, 404 y preflights, y en las respuestas de errores del router (`frameworkErrors`): `Content-Security-Policy: default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; sandbox`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy` y `Cross-Origin-Resource-Policy: same-origin`, `X-Permitted-Cross-Domain-Policies: none`, `X-DNS-Prefetch-Control: off`, `X-XSS-Protection: 0` y `Cache-Control: no-store` por defecto (las rutas cacheables, como `/openapi.json`, lo pisan). `Strict-Transport-Security: max-age=63072000; includeSubDomains` solo en producción. `X-Powered-By` y `Server` se borran en `onSend`. Sin dependencia nueva (`@fastify/helmet` trae la política para HTML, que acá sobra).
- **CORS revisado, sin cambios de diseño**: lista exacta de orígenes, sin comodines ni `null`, credenciales solo para esos orígenes, `Vary: Origin`; en producción todos los `WEB_ORIGINS` tienen que ser https.
- **Validación estricta**: todo `params`, `query` y `body` del contrato es `z.strictObject` en todos los niveles; una clave desconocida es `400 validation_failed` (`unrecognized_keys`), nunca se descarta en silencio (OWASP API3:2023, asignación masiva). `defineEndpoint` recorre los esquemas de entrada al cargar y falla si encuentra un objeto que no lo sea, así ningún endpoint nuevo se escapa. Las respuestas siguen abiertas (agregar un campo no rompe clientes, ADR 0020). El parser JSON rechaza `__proto__` y `constructor.prototype`.
- **Límites de tamaño**: `BODY_LIMIT_BYTES` global (1 MiB por defecto, 10 MiB como máximo configurable), 16 KiB para la clase `auth`, params de ruta de hasta 100 caracteres (más largo es `404` sin eco del path), request line + headers hasta `HTTP_MAX_HEADER_SIZE_BYTES` (16 KiB; Node responde `431`). Un body excedido responde **`413 payload_too_large`**, código nuevo del catálogo (antes salía `400 bad_request`). Los archivos (videos, logos, PDFs) **nunca pasan por la API**: B-325 (#56) los sube al bucket con URLs firmadas cuyo tamaño máximo firma la API; la clase `upload` queda para esos endpoints.
- **Timeouts y conexiones del servidor**, configurables y validados: request completo `HTTP_REQUEST_TIMEOUT_MS` (30 s), headers `HTTP_HEADERS_TIMEOUT_MS` (10 s, nunca mayor que el anterior), keep-alive `HTTP_KEEP_ALIVE_TIMEOUT_MS` (72 s, por encima del idle del proxy), socket inactivo `HTTP_CONNECTION_TIMEOUT_MS` (60 s) y `HTTP_MAX_CONNECTIONS` (2048 por réplica). El tiempo de los handlers lo acotan `DATABASE_STATEMENT_TIMEOUT_MS` y el socket inactivo.
- **Secretos**: todos salen del entorno validado con zod; los mensajes de error nombran la variable y el problema, nunca el valor (los mensajes propios se muestran, los de zod solo por código). En producción la API no arranca con un `AUTH_SECRET` de menos de 32 caracteres, con menos de 128 bits de entropía estimada (largo × entropía de Shannon por carácter) o con pinta de valor de ejemplo (`change-me`, `example`, `secret`, `password`, `placeholder`); con un `RESEND_API_KEY` de menos de 20 caracteres; con un `DATABASE_URL` o `AUTH_DATABASE_URL` sin contraseña, con una de menos de 16 caracteres o de ejemplo; con los dos iguales; ni con `RATE_LIMIT_ENABLED=false`. pino redacta además `*.secret`, `*.apiKey`, `*.authorization`, `*.cookie`, `*.otp`, tokens y connection strings; al arrancar se loguea un resumen de la configuración sin secretos (`configSummary`).
- **Checklist OWASP** en [`docs/security/api.md`](../security/api.md): cada ítem de ASVS que aplica y cada riesgo del API Security Top 10 (2023) apunta a código y tests o a un issue abierto. Se revisa antes del primer deploy a producción y en cada issue que agregue superficie (archivos, importaciones, notificaciones).

## Alternativas descartadas

- **`@fastify/rate-limit`.** Su store de Redis es infraestructura nueva (ADR 0011 y 0028 ya la evitaron); el de memoria no sirve con varias réplicas, y un store propio sobre Postgres sería reescribir lo que ya hay.
- **Límite general en memoria por réplica** (con el de Postgres solo para el ingreso). Más barato, pero con N réplicas el límite real es N veces el declarado y cambia con cada escalado.
- **Contar por IP antes de autenticar** y por usuario después. Dos viajes a la base por request con sesión, para ahorrar una búsqueda de sesión solo cuando la IP ya está bloqueada.
- **Fallar cerrado en el límite general.** Una base de auth lenta dejaría toda la API respondiendo `500`.
- **Descartar claves desconocidas** (el comportamiento por defecto de zod). Esconde errores de los clientes y deja la puerta abierta a asignación masiva cuando un handler pasa el body entero al ORM.
- **`@fastify/helmet`.** Su configuración por defecto es para páginas HTML (CSP con `self`, `upgrade-insecure-requests`); para una API JSON hay que desactivar casi todo y la política propia es más corta y explícita.

## Consecuencias

- Cada request hace una transacción más en el pool de auth (`AUTH_DATABASE_POOL_MAX`, 5 por defecto); con carga alta hay que subirlo. Las filas `api_*` de `auth_rate_limit` se borran con la poda horaria de ADR 0028.
- La tabla se sigue llamando `auth_rate_limit` aunque ahora guarde también los contadores generales; renombrarla es una migración sin beneficio funcional.
- Un cliente que manda claves que el contrato no describe (campos viejos, `_` para evitar caché) ahora recibe `400`. Web y mobile usan el cliente tipado, que solo manda lo que el contrato describe.
- Un equipo entero detrás del NAT del club comparte los contadores por IP; los valores por defecto contemplan unas 40 personas sincronizando a la vez. Si un club supera eso, se suben las constantes de `DEFAULT_ROUTE_CLASS_LIMITS` (un deploy) o se pasa a límites por club.
- `payload_too_large` es un código nuevo: los clientes lo traducen como cualquier otro (y deben tolerar códigos que no conocen, ADR 0020).
- En producción hay que cargar un `AUTH_SECRET` generado (`openssl rand -base64 48`) y logins de base con contraseña fuerte (`DB_LOGIN_PASSWORD=$(openssl rand -base64 32)` al correr `db:provision-login`); con valores de ejemplo la API no arranca.
