# 0096. Tests de punta a punta: stack real con el club demo, código de ingreso leído del log de la API, Playwright para la web y el motor de la app sin dispositivo

- Estado: Aceptado
- Fecha: 2026-11-04
- Issue: #21 (B-108)

## Contexto

B-108 pide Playwright para la web y Maestro para mobile, corriendo en CI contra el club demo. Los tests unitarios de la web usan una API falsa y los de la API usan `inject`: nada probaba que la web compilada, la API compilada, el worker y Postgres funcionen juntos con los roles de conexión, la RLS, la cookie de sesión y el CORS reales. Había que decidir dónde viven estos tests, cómo se arma el entorno, cómo se ingresa (el ingreso es solo por código de email, ADR 0010, y el código se guarda hasheado), de dónde salen los datos, qué parte de mobile corre en CI sin dispositivos y cómo entra en el check `ci` sin alargar el resto.

## Decisión

- **Paquete propio `apps/e2e`** (`@sport-performance/e2e`): el stack, el arnés y los escenarios de Playwright. No compila nada; sus tests unitarios (Vitest, `src/**`) prueban el arnés y corren en `pnpm test`; los escenarios (`tests/`) corren solo con `pnpm --filter @sport-performance/e2e e2e`.
- **El stack es el de un ambiente** (`src/stack/main.ts`, TypeScript corrido por Node con type stripping): una base nueva en el servidor de `E2E_DATABASE_URL` (se crea al arrancar y se borra, con sus logins, al bajar el stack; también al arrancar, por si una corrida anterior murió sin bajarlo; declara `app.deployment_environment = 'test'`), todas las migraciones, un login por rol de conexión con el nombre de la base como prefijo (`sport_performance_e2e_api`, `_worker`, `_auth`: los roles son de todo el servidor, así que dos stacks con distinto `E2E_DATABASE_NAME` no se pisan las contraseñas; contraseñas al azar por corrida que solo viajan en el entorno de los hijos; ADR 0026), el club demo sembrado con `runDemoSeed` (lo mismo que `db:seed:demo`, con su guarda; ADR 0055), la API y el worker compilados (`dist/`) y la web compilada servida por `vite preview`. Todo en `127.0.0.1` (API 3100, web 4174): web y API son el mismo sitio y la cookie `HttpOnly` viaja como en producción. El `AUTH_SECRET` es nuevo en cada corrida. Está listo cuando la web responde, y la API ya respondió `/health/ready`. Se niega a arrancar si la web no se compiló con `VITE_API_URL` apuntando a esta API.
- **Club demo propio:** slug `demo-e2e`, semilla `e2e`, 35 días de historia (más que los 28 de la EWMA crónica, menos que los 84 de staging, por el tiempo de CI). El generador es puro (ADR 0055): el arnés recalcula el mismo dataset con las opciones que el stack deja en `state.json` y los escenarios eligen a su gente de ahí (el jugador de una categoría asignada, el que tuvo una lesión, los hijos de la familia) en vez de nombres copiados. `state.json` se valida con un esquema `zod` al leerlo: uno viejo o ajeno falla diciendo qué campo no cuadra.
- **El demo se genera hasta hoy, no hasta un día fijo:** la API y la base calculan el día del club con el reloj real (`app.club_today()`, `now()`), y la disponibilidad, el panel y las ventanas de 90 días se miden desde ahí; un dataset cortado en otra fecha quedaría fuera de esas ventanas. El dataset es reproducible para un mismo día (generador puro y semilla fija), y el día queda en `state.json`.
- **Fixtures del stack para lo que el calendario no garantiza:** el generador solo lesiona en temporada (febrero a noviembre), así que en el receso ningún jugador de M17/M19 de rugby tiene una restricción en los últimos 90 días. El stack agrega una lesión abierta hoy, con un diagnóstico único por corrida (`Lesión ficticia (knee) E2E <uuid>`), a un jugador de esas categorías con el que ningún escenario ingresa, escrita como escribe el seed los datos de salud, y la deja en `state.json`; el escenario del entrenador la usa y falla en vez de saltearse.
- **El código de ingreso sale del log de la API, no de la base ni de una puerta trasera.** Sin `RESEND_API_KEY` la API ya escribe cada email en su log (`LogEmailTransport`, ADR 0054); el stack lee las líneas JSON de su salida y deja los emails de ingreso en `mailbox.jsonl` (destinatario, tipo, código, links). La API no tiene nada nuevo ni ningún modo de test; en producción `RESEND_API_KEY` es obligatoria, así que esto no existe ahí. Un test del arnés renderiza el email con el mailer real de la API para que el parser no se desacople de la plantilla.
- **Sesiones por cuenta reutilizadas:** el proyecto `setup` abre una sesión por cuenta del demo (administración, entrenadores, PF, médico, familia, jugador y jugadora) por la API, como la pantalla de ingreso (`email-otp`, `verify` con `transport: cookie` y el `Origin` de la web), y la guarda como storage state; los escenarios la usan. Los límites de ingreso por email e IP (ADR 0028) quedan lejos y los límites generales siguen activos. La pantalla de ingreso misma (código incorrecto, correcto, cerrar sesión) tiene su escenario.
- **Los textos salen del catálogo** `es-AR` de `packages/i18n` (`createTranslator`), y los elementos se buscan por rol y nombre accesible: un cambio de texto no rompe los tests y un control sin nombre accesible sí.
- **Escenarios de la web:** ingreso por código; cada rol en su lugar (el jugador va a "usá la app", el tutor solo al área de familia con sus hijos, la administración ve usuarios y roles, el entrenador no ve la administración); el entrenador ve solo sus categorías asignadas; un jugador que tuvo una lesión figura "No disponible" y el texto del diagnóstico no aparece en la página del entrenador; el entrenador crea una sesión y la vuelve a encontrar después de recargar.
- **Mobile en CI sin dispositivos:** el cliente de la app (`createMobileApi`), su `SessionController` y su motor de sincronización (ADR 0050, 0069) sobre SQLite real (`node:sqlite`, las mismas migraciones que `expo-sqlite`) contra la API del stack: ingreso por código con token bearer, bienestar cargado sin red que queda en la cola, se sube por `/v1/sync/push` al volver la red y su fila vuelve por `/v1/sync/changes`. Vive en `apps/mobile/e2e` (usa el código de la app) con su propia config de Vitest (`test:e2e`), fuera de `pnpm test`, y usa el arnés de `@sport-performance/e2e/harness`.
- **Maestro queda fuera de CI:** la UI nativa necesita un dev build (ADR 0013) y un emulador o dispositivo; un runner de Linux con emulador de Android y un build nativo por PR multiplica el tiempo de CI y depende de EAS. Se documenta en `apps/mobile/README.md` qué flujos cubriría y qué hace falta para correrlo; los flujos y su job llegan cuando haya un dev build reproducible en CI.
- **CI:** job `e2e` aparte (en paralelo con los demás, en el `needs` del check `ci`): Postgres de servicio, build de la API, el worker y la web (con `VITE_API_URL`, que es parte del hash de Turborepo), Chromium de Playwright cacheado por versión, el stack en segundo plano una vez para la web y mobile, al final se baja el stack (y con él la base), y en una falla el reporte HTML, trazas, capturas, video y los logs del stack como artefacto. Solo Chromium: la web es para el staff en escritorio y el costo de otros motores no se justifica todavía.

## Consecuencias

- Correr en local: `E2E_DATABASE_URL=postgres://… pnpm --filter @sport-performance/e2e e2e` (con la API, el worker y la web compilados como dice el README). Playwright levanta el stack o usa uno que ya esté corriendo (`e2e:stack` en otra terminal, para iterar).
- Un escenario nuevo elige sus datos del dataset y escribe solo filas propias (títulos únicos): los escenarios corren en paralelo sobre el mismo club.
- Los escenarios dependen del día: el club demo se genera hasta hoy. Si un escenario necesita algo que el calendario no da todos los días (por ejemplo, una lesión en los últimos 90 días en el receso), el stack lo agrega como fixture y el escenario falla si no está; nunca se saltea en silencio.
- Las métricas derivadas las calcula el worker del stack después del seed; ningún escenario espera a que termine. Un escenario del panel con alertas tendría que esperar al outbox.
- Las cuentas del demo (`<slug>.<rol>@example.com`, RFC 2606) nunca reciben correo; el mailbox es solo del stack de prueba.
