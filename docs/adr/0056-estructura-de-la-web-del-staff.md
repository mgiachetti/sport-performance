# 0056. Estructura de la web del staff: rutas por sesión y club, datos por el cliente tipado, tema en runtime y estado de conexión

- Estado: Aceptado
- Fecha: 2026-11-03
- Issue: #64 (B-401)

## Contexto

El ADR 0012 eligió React + Vite + TanStack Router + TanStack Query para la web del staff, y la API ya tiene todo lo que la web necesita para arrancar: login por código con sesión en cookie (ADR 0028), membresías y `X-Membership-Id` (ADR 0007), soporte del superadmin por headers (ADR 0032), tema público del club (`GET /v1/clubs/{slug}/theme`), categorías y asignaciones del staff (ADR 0034), la matriz de permisos en el dominio (ADR 0025), el sobre de error único y el cliente tipado de `packages/contracts` (ADR 0020), y `X-Api-Version` en cada respuesta (ADR 0045, que dejó a este issue qué hacer con una pestaña vieja). Faltaba decidir cómo se arma la web encima de eso para que las pantallas que vienen (#65–#78) no repitan cada una cómo se elige el club, cómo se cachea, cómo se muestra un error, cómo se decide qué ve cada rol y cómo se prueba.

## Decisión

- **Árbol de rutas por código** (`apps/web/src/router.tsx`), sin generador de archivos: `/login`; `_authed` (exige sesión con `GET /v1/me`; sin sesión va a `/login?redirect=`); dentro, `/clubs` (selector), `/support` (solo superadmin) y `_club`, el layout de todo lo que pasa dentro de un club. Una pantalla nueva es un hijo de `_club` más una entrada en `layout/navigation.ts`. El `?redirect=` solo acepta rutas internas (`/…`, nunca `//host`), para que un link armado no saque al usuario del sitio después de ingresar.
- **Sesión:** la cookie `HttpOnly` de la API (`transport: 'cookie'`, `credentials: 'include'`); la web nunca ve un token ni lo guarda. Un `401` en cualquier pedido que no sea el del código, con una sesión que existía, limpia la caché y vuelve a `/login?expired=true&redirect=<donde estaba>`; un `401` en la primera visita no es "sesión vencida". Al ingresar y al salir se vacía la caché; al salir, también la selección de club, para que la próxima persona en una compu compartida empiece de cero. Si el `sign-out` no llega a la API, el usuario sigue adentro y ve el error: la sesión seguiría abierta.
- **Club:** la selección es la membresía (se recuerda en `localStorage`, no es secreta: la API la valida en cada pedido) o el modo soporte del superadmin (club + motivo, solo en `sessionStorage`: termina con la pestaña y una pestaña nueva pide el motivo otra vez). Un único lugar (`ClubSelectionStore.headers()`) agrega `X-Membership-Id` o `X-Support-Club-Id` + `X-Support-Reason` (percent-encoding) a cada pedido del cliente. Con una sola membresía se entra directo; con varias, o si la recordada ya no es del usuario, se pasa por el selector, que después vuelve a donde iba. **El club no va en la URL**: un link compartido lleva deporte y categoría y se abre en el club activo de quien lo recibe; lo que ese usuario no ve se ignora con un aviso.
- **La web es del staff:** `coach`, `sc`, `medical`, `admin` y superadmin en soporte. Una membresía `player` o `parent` ve "la web es para el staff, usá la app" y la web no pide datos del club con ella.
- **`ActiveClub`:** el layout del club arma, desde la caché que llenó el `loader` de la ruta, quién es, con qué rol, en qué club (`GET /v1/club`, que trae la zona horaria), la marca (`getClubTheme`), las asignaciones vigentes (`GET /v1/me/staff-assignments?status=current`, solo para los roles con alcance `assigned`) y las categorías que ve (`GET /v1/categories`, que la API ya filtra por asignación). De ahí sale el **sujeto de la matriz de permisos** (ADR 0025): la navegación (`visibleNavItems`) y las acciones (`useCan`, `<Can>`, `<RequirePermission>`) se deciden con `can()` del dominio, sin reglas propias de la web; la API vuelve a decidir.
- **Deporte y categoría** del layout van en los search params (`?sport=&category=`), validados contra las categorías que el usuario ve (`resolveScope`) y retenidos entre pantallas del club con `retainSearchParams`. Para sacar uno se navega con el valor `undefined` explícito.
- **Datos:** todas las llamadas por el cliente tipado de `packages/contracts`, envuelto una sola vez (`createWebApiClient`) para mandar la cookie y los headers del club y para alimentar el estado de conexión. Las claves de TanStack Query tienen tres raíces: `['session', …]`, `['public', …]` y `['club', <selección>, …]`; todo lo del club lleva la selección en la clave, así un club nunca contesta una consulta de otro. Las rutas esperan los datos con `ensureQuery` (lo que haya en caché, si no, pedirlo) y las pantallas los leen con `useSuspenseQuery`, que revalida en segundo plano. Las listas chicas que el shell necesita enteras siguen el cursor (`fetchAllPages`, con tope).
- **Reintentos:** las consultas reintentan solo errores transitorios (sin respuesta, `502`–`504`, `429` con `Retry-After`, respetándolo), nunca otros `4xx` ni un `500`. Las mutaciones reintentan solo cuando no hubo respuesta: toda alta lleva `clientUuid` y toda edición `expectedVersion` (ADR 0032), así reenviar no duplica ni pisa. Una pantalla que muta tiene que cumplirlo.
- **Errores:** `describeError` es la única traducción del sobre de error a texto: un mensaje de `packages/i18n` por cada código de `ERROR_STATUS` (un test falla si falta uno), códigos desconocidos por clase de status, el `requestId` visible como "Código para soporte", `ApiNetworkError` como "sin conexión" y `ApiContractError` (o un `426`) como "recargá". El `message` del sobre es para desarrolladores y no se muestra. Cada ruta tiene error boundary con reintento y hay página 404.
- **Conexión y sincronización:** `ConnectionStore` junta `navigator.onLine` y si la API contesta (cualquier respuesta la marca alcanzable; un pedido sin respuesta, no abortado, la marca caída) y maneja el `onlineManager` de TanStack Query: sin conexión o sin API, consultas y mutaciones se pausan y siguen solas al volver; mientras tanto se prueba `/v1/health` cada 10 s. El shell muestra siempre el estado con ícono y texto y `aria-live`: en línea, sin conexión, sin servidor, cambios en espera (mutaciones pausadas) y hora de la última respuesta en la zona del club. La web no guarda cola offline en disco: lo pausado vive en la pestaña y el texto lo dice; la carga sin conexión de verdad es de mobile (ADR 0015).
- **Pestaña vieja:** si el `X-Api-Version` de una respuesta tiene otra versión mayor o menor que el `CONTRACT_VERSION` con el que se construyó la web, aparece "Hay una versión nueva de la web, recargá". El parche no cuenta: no cambia la forma del contrato.
- **Tema en runtime:** `ThemeStore` (marca del club activo, ORC antes de elegir; preferencia del usuario `system` | `dark` | `light-hc` en `localStorage`; `prefers-contrast: more` del sistema para `system`) y `ThemeController`, que aplica `createTheme` de `packages/ui-tokens` como variables `--sp-*` y `data-theme` en `<html>` antes de pintar. El CSS de la web solo usa esas variables: ningún hex. Una marca inválida cae a la de ORC, nunca rompe la UI. Barlow y Barlow Condensed se sirven desde el propio build (`@fontsource`, sin CDN de terceros).
- **Accesibilidad:** foco visible con el token `focus` en todo control, "Saltar al contenido", landmarks (`aside`/`nav`/`header`/`main`), `lang="es-AR"`, título del documento por pantalla y foco en el título al navegar; selectores nativos; estados siempre con ícono y texto.
- **Entorno:** `VITE_API_URL` es la única variable, validada al arrancar (https en producción salvo `localhost`); la API tiene que tener el origen de la web en `WEB_ORIGINS`.
- **Tests:** Vitest + Testing Library sobre jsdom. `renderApp()` monta la app entera (providers, router con historia en memoria, tema, conexión) sobre una **API falsa por `operationId`** del catálogo de contratos (`test/fake-api.ts`): las respuestas pasan por la validación del cliente real, así un fixture que no cumple el contrato falla el test. `signedIn()` / `signedOut()` arman los handlers de sesión y club; las pantallas se prueban como las ve el usuario (roles, textos, URL).

## Consecuencias

- Cada pantalla nueva: una ruta hija de `_club`, sus consultas con `clubQueryKey`, su entrada de navegación con el permiso de la matriz, sus textos en `packages/i18n` y sus tests con `renderApp`.
- Cambiar de club recarga lo del club desde cero (otra clave); no hay datos mezclados aunque una pantalla olvide invalidar.
- Un link compartido no cambia el club de quien lo abre. Si hace falta abrir el club del link, se agrega el slug a la URL con un ADR nuevo.
- La web no muestra pantallas a jugadores ni tutores; si algún día las necesita, la decisión se revisa.
- Los headers de seguridad del sitio estático (CSP, HSTS) y el deploy quedan para B-701; la web no usa recursos de terceros, así que la CSP puede ser `default-src 'self'` más el origen de la API y del bucket de los escudos.
